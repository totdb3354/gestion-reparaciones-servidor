1. De donde venimos: el modelo anterior

En el modelo anterior, el programa JavaFX conectaba directamente a la base de datos MySQL usando JDBC. Cada DAO tenía su propia Connection y lanzaba consultas SQL:

// Antes — DAO conectando directamente a MySQL
public class ComponenteDAO {
    public List<Componente> getAll() throws SQLException {
        Connection con = Conexion.getConnection();           // abre conexión
        PreparedStatement ps = con.prepareStatement(
            "SELECT * FROM Componente");
        ResultSet rs = ps.executeQuery();
        // ... mapear resultados ...
    }
}

Esto funcionaba bien cuando el programa y la base de datos estaban en el mismo ordenador. Pero si querías acceder desde otro PC de la tienda, o desde casa, había un problema: los puertos de MySQL no suelen estar expuestos a Internet, y conectar a una BD directamente desde fuera de la red local es inseguro y complicado.

La solución es separar la lógica en dos piezas:

🖥️ Cliente JavaFX Solo la interfaz. Pide datos por HTTP.
↕ HTTP / JSON
⚙️ Servidor Spring Boot Recibe peticiones, ejecuta la lógica, habla con la BD.
↕ JDBC / SQL
🗄️ MariaDB Base de datos. Solo accesible desde el servidor.
💡 Analogía Piensa en un restaurante. El cliente (tú) habla con el camarero (API REST). El camarero va a cocina (base de datos) y trae el plato. El cliente nunca entra en la cocina directamente.

2. ¿Qué es Spring Boot?

Spring Boot es un framework de Java que convierte tu programa en un servidor web. Cuando lo arrancas con mvn spring-boot:run, levanta un servidor HTTP en el puerto 8080 que escucha peticiones de cualquier cliente (el JavaFX, un navegador, Postman…).

Lo más importante que hace Spring Boot por ti:

  • Inyección de dependencias — no tienes que crear objetos con new. Le dices a Spring qué necesitas y él los crea y los conecta solos.
  • Servidor web embebido — lleva un Tomcat por dentro, no hay que instalarlo aparte.
  • Mapeo de URLs — con anotaciones como @GetMapping le dices qué método se ejecuta cuando llega cada petición.
  • Serialización automática — convierte los objetos Java a JSON (y viceversa) usando Jackson, automáticamente.
⚠️ Inyección de dependencias Si ves que una clase tiene un constructor que recibe otra clase como parámetro y no hay ningún new en ningún sitio, es inyección de dependencias. Spring crea la instancia y la "inyecta" automáticamente porque la clase tiene @Repository, @Service o @Component. 
// Spring crea ComponenteDAO automáticamente y lo pasa al controller
@RestController
public class ComponenteController {
    private final ComponenteDAO dao;

    public ComponenteController(ComponenteDAO dao) {  // Spring inyecta
        this.dao = dao;
    }
}

4. Los modelos model/

Son exactamente lo mismo que tenías antes: clases Java simples (POJOs) que representan una fila de la base de datos. No tienen lógica, solo campos, constructor y getters.

La única diferencia es que ahora también sirven para serializar/deserializar JSON. Jackson (la librería incluida en Spring Boot) convierte automáticamente Componente → JSON usando los getters de la clase:

// Java
new Componente(1, "bati iPhone 12", 5, 2, true)

// Jackson lo convierte automáticamente a JSON:
{
  "idCom": 1,
  "tipo": "bati iPhone 12",
  "stock": 5,
  "stockMinimo": 2,
  "activo": true
}
✅ Regla de oro Jackson usa los getters para serializar (Java → JSON). Si el getter se llama getIdCom() → la clave JSON es "idCom". Si es isActivo() → la clave es "activo". Por eso en el cliente, Gson puede deserializar si los campos tienen el mismo nombre.

5. Los DAOs dao/

Los DAOs hacen exactamente lo mismo que antes: hablar con la base de datos usando SQL. La diferencia es que ya no gestionan la conexión ellos mismos. Usan JdbcTemplate, que Spring les inyecta automáticamente.

JdbcTemplate — el sustituto de Connection + PreparedStatement

JdbcTemplate es la herramienta de Spring para ejecutar SQL. Tiene dos operaciones principales:

MétodoPara quéEquivalente antiguo
jdbc.query(sql, mapper, params...)SELECT → Listps.executeQuery() + while(rs.next())
jdbc.queryForObject(sql, tipo, params...)SELECT → 1 valorrs.next(); rs.getInt(1)
jdbc.update(sql, params...)INSERT/UPDATE/DELETEps.executeUpdate()
// ANTES — manual y verboso
Connection con = Conexion.getConnection();
PreparedStatement ps = con.prepareStatement(
    "SELECT * FROM Componente WHERE ID_COM = ?");
ps.setInt(1, idCom);
ResultSet rs = ps.executeQuery();
if (rs.next()) {
    return new Componente(rs.getInt("ID_COM"), rs.getString("TIPO"), ...);
}

// AHORA — con JdbcTemplate
return jdbc.queryForObject(
    "SELECT * FROM Componente WHERE ID_COM = ?",
    (rs, row) -> new Componente(rs.getInt("ID_COM"), rs.getString("TIPO"), ...),
    idCom);

El (rs, row) -> new Componente(...) es el RowMapper: una función lambda que convierte una fila del ResultSet en un objeto Java. Es exactamente lo que hacías tú dentro del while(rs.next()), pero más compacto.

@Transactional — transacciones sin try/finally

Antes, para hacer una transacción (varias operaciones que deben ir juntas o no ir) tenías que hacer con.setAutoCommit(false), ejecutar las queries, hacer con.commit() y en el catch hacer con.rollback(). Con Spring basta poner @Transactional en el método y él lo gestiona automáticamente:

@Transactional
public void confirmarRecibido(int idCompra, LocalDateTime updatedAt) {
    // Si cualquiera de estas dos líneas falla, se hace rollback automático
    jdbc.update("UPDATE Compra_componente SET ESTADO='recibido' WHERE ID_COMPRA=?", idCompra);
    jdbc.update("UPDATE Componente SET STOCK = STOCK + ? WHERE ID_COM=?", cantidad, idCom);
}

6. Los controllers controller/

Los controllers son el elemento nuevo respecto a tu arquitectura anterior. Son las clases que reciben las peticiones HTTP del cliente JavaFX, llaman al DAO correspondiente y devuelven la respuesta.

Cada controller gestiona una ruta de la API (por ejemplo, /api/componentes) y dentro tiene un método por cada operación posible:

@RestController                          // Esta clase atiende peticiones HTTP
@RequestMapping("/api/componentes")      // Todas sus rutas empiezan por /api/componentes
public class ComponenteController {

    private final ComponenteDAO dao;     // Spring inyecta el DAO

    @GetMapping                           // GET /api/componentes
    public List<Componente> getAll() {
        return dao.getAll();              // Llama al DAO, Jackson convierte a JSON
    }

    @GetMapping("/stock-bajo")           // GET /api/componentes/stock-bajo
    public List<Componente> getStockBajo() {
        return dao.getStockBajo();
    }

    @PostMapping                          // POST /api/componentes
    @ResponseStatus(HttpStatus.CREATED)   // Devuelve código 201 en vez de 200
    public void insertar(@RequestBody InsertarRequest req) {
        dao.insertar(req.tipo(), req.stock(), req.stockMinimo());
    }
}

Records como clases de request

Dentro de los controllers verás clases record privadas. Sirven para representar el cuerpo JSON que llega en las peticiones, de forma compacta:

// En vez de crear una clase completa con constructor + getters...

// Jackson mapea este JSON automaticamente a ese record:
// { "tipo": "bati iPhone 13", "stock": 10, "stockMinimo": 3 }

7. La capa de seguridad

Este es el bloque más diferente respecto a lo que conocías. Antes, la seguridad era simplemente comprobar usuario/contraseña contra la BD y guardar quién estaba conectado en una variable. Ahora, como el servidor es sin estado (no recuerda a los clientes entre peticiones), se usa un sistema de tokens JWT.

¿Qué es un JWT?

🎫 Analogía: el pulsera de festival Cuando llegas al festival, compras la entrada y te dan una pulsera. Ya no necesitas volver a la taquilla: con enseñar la pulsera en cada zona te dejan pasar. El JWT funciona igual: el cliente hace login UNA VEZ, recibe un "token" (la pulsera) y lo manda en cada petición posterior. El servidor verifica la pulsera sin consultar la BD.

Un JWT tiene tres partes separadas por puntos: CABECERA.DATOS.FIRMA. La parte de datos (payload) contiene quién eres, tu rol y cuándo expira. La firma garantiza que nadie ha manipulado el token.

// El cliente manda esto en cada petición HTTP:
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhZG1pbiIs...

Las 5 clases de seguridad

1. UsuarioPrincipal

Es el objeto que representa al usuario autenticado. Implementa UserDetails, que es la interfaz que Spring Security entiende. Contiene: ID de usuario, nombre, contraseña (hash), rol y ID de técnico (si aplica).

2. UserDetailsServiceImpl

Solo se usa en el momento del login. Spring Security la llama con el nombre de usuario, esta clase hace una consulta SQL para buscarlo (con JOIN a Tecnico para comprobar que está activo) y devuelve un UsuarioPrincipal. Spring compara el hash de la contraseña usando BCrypt.

// Solo se ejecuta al hacer login:
SELECT u.ID_USU, u.NOMBRE_USUARIO, u.PASSWORD, u.ROL, u.ID_TEC
FROM Usuario u
LEFT JOIN Tecnico t ON u.ID_TEC = t.ID_TEC
WHERE u.NOMBRE_USUARIO = ?
  AND (u.ID_TEC IS NULL OR t.ACTIVO = 1)
-- Los admins (ID_TEC IS NULL) siempre pueden entrar.
-- Los técnicos solo si Tecnico.ACTIVO = 1.

3. JwtUtil

Tiene dos responsabilidades: generar el token al hacer login (firmándolo con una clave secreta configurada en application.properties) y verificar/leer el token que llega en cada petición posterior.

// Genera el token con estos datos:
{
  "sub":   "admin",      ← nombre de usuario
  "idUsu": 1,           ← ID del usuario
  "rol":   "ADMIN",     ← rol
  "idTec": null,        ← ID del técnico (solo si es técnico)
  "exp":   1745704000   ← expira en 24h
}

4. JwtAuthFilter

Es un filtro HTTP: se ejecuta automáticamente en cada petición, antes de que llegue al controller. Lee el token del header Authorization, lo verifica con JwtUtil, extrae los datos del usuario (sin consultar la BD) y le dice a Spring Security "este usuario está autenticado".

// Lo que hace en cada petición:
1. Leer header: "Authorization: Bearer eyJ..."
2. Verificar firma del token → si es inválido, devuelve 401
3. Extraer datos (username, rol, idTec) del token
4. Crear UsuarioPrincipal SIN consultar BD
5. Registrar en SecurityContext → Spring sabe quién es

5. SecurityConfig

Es la clase de configuración general. Define las reglas de seguridad:

  • /api/auth/login → acceso libre (sin token)
  • Todo lo demás → requiere token válido
  • Sin sesión HTTP (stateless) — cada petición es independiente
  • Sin protección CSRF (no aplica en APIs REST)
✅ Flujo completo de login Cliente manda usuario+contraseña → AuthController recibe → AuthenticationManager llama a UserDetailsServiceImpl → busca en BD → BCrypt verifica contraseña → si OK, JwtUtil genera token → el cliente lo guarda y lo manda en todas las peticiones siguientes.

8. Flujo completo de una petición

Supongamos que el cliente JavaFX quiere obtener la lista de componentes con stock bajo. Aquí está todo lo que ocurre, paso a paso:

1
Cliente envía: GET http://localhost:8080/api/componentes/stock-bajo con el header Authorization: Bearer eyJ...
2
JwtAuthFilter intercepta: lee el token, verifica la firma, extrae el rol y el ID de usuario. Registra en el contexto de seguridad. No hace ninguna consulta a la BD.
3
SecurityConfig comprueba: esta ruta requiere autenticación. El usuario ya está autenticado (lo hizo el filtro), así que deja pasar.
4
ComponenteController.getStockBajo() recibe la petición. Llama a dao.getStockBajo().
5
ComponenteDAO ejecuta la SQL: SELECT ... FROM Componente WHERE STOCK <= STOCK_MINIMO AND ACTIVO = 1 y devuelve una lista de objetos Componente.
6
Jackson serializa la lista a JSON automáticamente. El servidor responde con código 200 y el cuerpo JSON.
7
ApiClient en el cliente recibe el JSON y Gson lo deserializa a List<Componente>. El controller JavaFX actualiza la tabla.

9. Control de concurrencia optimista (Optimistic Locking)

Cuando dos usuarios editan el mismo registro a la vez, puede haber un conflicto. El sistema usa una técnica llamada control de concurrencia optimista para detectarlo sin bloquear la base de datos.

Cada tabla que necesita este control tiene un campo UPDATED_AT (tipo TIMESTAMP) que MariaDB actualiza automáticamente cada vez que se modifica la fila.

⚠️ ¿Cómo funciona?
  1. El cliente lee el registro → recibe también el updatedAt
  2. El usuario hace cambios
  3. Al guardar, manda también el updatedAt que tenía cuando lo leyó
  4. El servidor compara ese updatedAt con el que hay en BD ahora
  5. Si son distintos → otro usuario modificó la fila → error 409 (Conflict)
  6. Si son iguales → nadie modificó nada → se hace el UPDATE
// Ejemplo en CompraComponenteDAO:
private void checkUpdatedAt(LocalDateTime bdAt, LocalDateTime clientAt) {
    if (!clientAt.truncatedTo(SECONDS).equals(bdAt)) {
        throw new ResponseStatusException(CONFLICT,
            "Dato modificado por otro usuario");
        // El cliente recibe código 409 → muestra diálogo de aviso
    }
}

# Clave secreta para firmar los JWT (mínimo 32 caracteres)
jwt.secret=cambiar-esto-en-produccion-min-32-caracteres

# Tiempo de expiración del token: 86400000 ms = 24 horas
jwt.expiration=86400000
🔒 Importante en producción El jwt.secret debe ser una cadena larga y aleatoria, guardada de forma segura (nunca en el repositorio de Git). Si alguien obtiene esa clave, puede generar tokens falsos.
